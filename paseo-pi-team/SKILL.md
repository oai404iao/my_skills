# Paseo + Pi 双层开发团队

## 显式调用与边界

仅在用户通过 `/skill:paseo-pi-team` 或明确点名本 skill / 这套双层团队流程时使用；普通开发、大型重构或泛泛提及多 agent 均不自动触发。若用户只是审查、修改本 skill 或索要方案，只完成该请求，不启动团队。

执行任务时，当前会话直接担任任务编排者，实际组织团队并推进交付，不再创建常驻“总指挥”或额外管理层。遵守宿主和目标项目的适用指令；本 skill 不增加工具权限，不替代用户授权。

Pi 的 `disable-model-invocation: true` 隐藏自动选择入口，仍保留显式命令；这不是文件访问控制，也不保证其他宿主支持同样语义。

## 输入与一次性授权

先从用户请求提取下列信息。`{{...}}` 是输入占位符，不是真实路径或既定业务要求；无需让用户重复已经明确的内容。

```text
项目路径：{{项目路径}}
任务目标：{{需要实现或重构的目标}}
验收结果：{{用户最终能观察到什么}}
明确不做：{{排除项；没有则写无}}
其他约束：{{兼容性、依赖、时间或成本要求}}
```

先读取项目指令、相关代码和当前 Git 状态，保护已有工作。参数缺失且影响实施时，提出最少必要问题，不猜测业务目标。

用户明确要求执行开发任务时，按其范围进行相关本地实现、测试和文档工作。启动时集中确认以下三项尚未明确的授权，允许分别同意或拒绝，并记录结果：

1. 是否允许在本任务执行分支创建本地提交；
2. 是否允许合入专用任务集成分支，以及采用的整合方式；
3. 是否允许在交付完整集成、相关验证通过且不再需要后，归档本任务新建的执行 workspace，并删除对应本地任务分支。

清理授权不含既有 workspace、用户原有分支、起始未提交修改、其他人的工作、任务集成工作区、最终交付分支、远程分支、业务数据或任务外资源。前三项授权均不等于允许 push、主分支合并、部署、真实迁移或业务写入；这些操作未经明确授权不得执行。

不要为普通可逆实现细节反复请示。授权阻塞时继续不受影响的工作；未获提交授权用明确基线的可应用 diff 交付，未获整合或清理授权则保留成果并说明阻塞。

## 1. 核实能力，形成最小路线

- 发现当前可用的 Paseo 工具并阅读实际 schema；不要凭旧示例猜参数。确认能识别当前编排者、workspace、源 checkout 和任务路径。
- 创建角色前读取 Paseo profiles 及每个 profile 的 notes，选择真实可用且适合任务的配置；按当前接口把配置应用到创建请求，不假设存在 `profile` 参数。必要时发现 provider、model 和能力；没有合适配置时说明情况，不编造模型名或配置。
- Pi 内部委派只使用当前 harness 实际提供的工具；Paseo 会话与 Pi subagent 不是同一层，也不保证每个角色都有相同工具。
- 给出最小实施路线及首个端到端验收切片，先确定该切片必需的跨模块接口，不先设计完整平台。
- 原生 workspace 能力缺失时报告相关隔离阻塞，不用手工 worktree 替代；heartbeat 缺失时报告监督能力限制，不声称已安排。继续不受影响的已授权工作，不伪造团队已启动。

## 2. 按交付边界分工

**Paseo 上层责任角色：**当前编排者、一位独立监督者，以及按可独立交付模块划分的执行角色。执行角色可承担设计、后端模块、前端或 QA；同类角色可以多个，不按头衔凑人数。设计工作小则由模块负责人承担。优先复用已有合适会话，避免重复创建。

并行度由可独立推进、可独立验证的切片决定。多个角色被同一根因阻塞时，指定一个 owner 处理共享阻塞，或改善隔离使问题可分解，不继续增加处理同一问题的执行者。

**Pi 角色内部成员：**上层角色可按实际需要委派局部研究、实现或具体风险审查，自己负责分工、检查和汇总。内部成员不创建 Paseo 团队、不接管跨角色调度、不越过所属角色写区，默认不递归建队；不因有工具就必须使用。Pi subagent 不等于独立 worktree，需另行保证写区不冲突。

**编排者：**负责最小验收结果、依赖和 ownership、派工与解除阻塞、及时集成、保持集成版本可验证，以及真实的最终报告。模块内部设计交给负责人，跨模块契约由相关负责人协商后收敛。不要将所有困难工作收回自己串行完成，也不要全部派出后只等待；优先处理接口阻塞、授权问题和可合入交付。

启动时明确两项职责：

- **集成 owner：**默认当前编排者，独占任务集成分支及工作区写入；发生实际吞吐瓶颈时可交给已有执行角色或 QA，不默认新增常驻集成管理角色。交接须说明当前版本、未完成操作和写入所有权。
- **最终集成验证 owner：**明确由谁验证当前集成版本，可由已有角色承担；编排者仍对最终验收结论负责。唯一集成写入 owner 不意味着所有设计、diff、测试都要排队审批。

## 3. 建立唯一当前任务表与工作区

复用项目已有机制，由编排者维护一份轻量当前任务表，明确唯一实际位置及访问方式。其他角色通过消息和交付反馈，不各自复制计划；不同 worktree 中的同名文件不是同步任务表，历史日志不能替代当前状态。

只维护：

- 交付项、负责人、模块 / 文件 ownership；
- agent ID、workspaceId、实际路径、分支、基线 commit；
- 依赖、关键接口、具体阻塞、当前状态和下一步；
- 交付源版本、集成结果版本、必要验证结果；
- 清理状态，或继续保留 workspace 的具体原因。

按工作区参考建立专用任务集成分支及工作区，保护起始工作区。新建独立代码写入角色时，先用 Paseo 原生 workspace 创建隔离，再显式绑定返回的 workspaceId，并核实路径、分支和 HEAD。编排者、监督者及唯一任务表不能依附将被提前清理的执行 workspace。

## 4. 启动独立监督，派发最小合同

创建或复用独立 Paseo 监督会话，交付监督参考、用户目标和授权、编排者 ID、任务表与集成工作区位置。由监督者在自己的会话建立原生 heartbeat，默认每 30 分钟检查一次，报告创建结果和 ID。不要把创建会话成功等同于监督定时器已建立。

每个执行角色的 initialPrompt / 后续任务只包含必要合同：

```text
目标与可观察完成条件：
基线 commit、workspaceId、实际路径、必要上下文：
拥有的模块 / 文件写区：
接口、依赖、明确不做：
本地提交、集成、清理及其他副作用的授权边界：
相关验证、交付对象、需升级给编排者的问题：
```

传达与该角色相关的简化设计、权限和验证要求；不只说“负责后端”，不复制整个主会话。执行角色对交付负责，内部讨论不转成编排者的新负担。

首次进展回复简短报告：「最小路线、角色分工、工作区、集成与验证 owner、监督是否已启动、授权阻塞」。只写实际状态，随后继续执行，不在输出团队名单或计划后停工。

## 5. 实施、切片交付与持续集成

先完成最小纵向闭环，再扩展。切片达到条件立即通知集成 owner，不等整个模块或团队完成；编排者下一轮调度优先处理可合入结果，避免扩大并行的同时堆积未集成交付。

执行角色负责相关检查、commit 或可应用 diff、模块冲突与语义修复；集成 owner 按依赖顺序实际整合，核查跨模块契约与受影响行为，并记录源版本、结果版本和检查。严格遵循工作区参考中的单写入 ownership、基线和授权边界。

交付说明只需：「完成行为、变更位置、提交或 diff、实际检查及对应版本、剩余问题」。披露接口偏差、未覆盖风险和消费者需要注意的变化，不倾倒完整 transcript。

始终区分「模块已交付」「已集成」「集成验证通过」「最终验收通过」。未经实际整合的成果不得报为已合并；不累加各 workspace 的通过数或编造完成百分比来表示整体完成。

### 简化设计与测试判断

- 只实现当前目标；默认不增加未请求的兼容层、迁移回填、长期双轨、假想扩展点、配置面、通用框架、无消费者元数据、重复状态或纯参数转发层。不另建任务平台、监控平台或复杂协调机制。
- 兼容性按用户明确要求处理；“完美、通用、长期”不是无限扩展授权。
- 测试保护行为与安全语义，不机械保护旧代码形状。产品缺陷保留有效回归并修产品；fixture 失效使用当前入口与最小 testkit 迁移；旧实现细节测试失效或重复时可删除或按新契约重写，说明仍有效行为由何处覆盖。
- 不为保留旧 CaseID、签名、callback 或异常顺序增加兼容，除非它确为有效契约。不通过删除真实缺陷用例、放宽安全断言、skip/xfail 或伪造来源刷绿。
- 身份隔离、授权、副作用、原子性、恢复安全仍须满足项目要求；改变业务对象归属或公开行为时明确决策，不自行猜测。
- 除项目要求或具体风险外，不强制逐断言 AST 映射、多重哈希封包、重复冷环境重放、每个小修改独立评审或多套冻结副本。

### 验证与纠偏

执行角色先运行相关检查并遵守仓库要求；QA 主要检查集成行为、跨模块边界和风险，不重复所有开发者的全部测试。切片合入后检查受影响集成行为，最终门禁按仓库要求完整执行，不能以局部通过代替。

记录检查对应版本，后续修改影响结果时补相关检查，不为无关修改机械重跑全部验证。集成失败时明确失败版本、责任模块和修复动作；必要时由集成 owner 撤销该次集成，保护其他已集成成果，不继续堆叠依赖失败版本的变更。

接受监督者的具体纠偏时说明落实动作并同步成员；不接受时给出简短事实依据；涉及用户目标、业务契约或授权冲突时向用户提出聚焦问题。外部多 agent 实验不构成放宽本项目安全要求或最终验收的依据。

## 6. 异步沟通与故障恢复

使用异步委派及完成通知，不高频轮询；监督抽查不等于全量重验。正常纠偏在安全边界传达，不随意打断长测试；发送消息前核实对运行中会话的实际语义，不混用 Paseo 和 Pi 工具约定。

工具接受消息仅表示提交。范围、接口、授权或写入 ownership 变更须由相关角色确认收到并落实；普通消息不建繁琐回执流程。空闲角色需后续工作时使用实际能启动其执行的接口，不能把仅投递消息当成已开始执行。

RPC 超时、模型失败、上下文压缩失败与项目测试失败分开报告。恢复前核对实际 agent / 进程状态、当前分支与 HEAD、落盘修改、已完成及未完成操作，以及是否仍在提交、合并、测试或归档。避免重复已成功但回执丢失的操作。

优先复用现有会话和已有成果，不因一次错误重建整队；未经授权不重启 daemon、杀进程、强制清理或覆盖他人工作。

## 7. 回收与最终交付

交付完整集成、相关集成验证通过且无继续使用需求时，集成 owner 按工作区参考及清理授权及时原生归档执行 workspace，再核查并处理对应本地任务分支，不统一拖到任务结束。执行角色只报告“可回收”，不提前自行归档。

未集成、验证失败、仍需排障或含未保留成果的 workspace 保留并记录原因；任务取消不代表可丢弃成果。集成工作区与最终交付分支默认留给用户。

达到目标并完成必要门禁后，由监督者删除自己的 heartbeat，报告实际结果，再按授权处理监督会话归档。若任务取消或不再需要监督，同样停止该任务 heartbeat，但不越权清理成果。

最终报告交付行为及位置、交付 / 集成版本、实际验证、保留资源和剩余阻塞。真实授权或环境阻塞无法继续时如实说明；不伪造启动、监督、集成、验证或清理结果。目标及必要门禁完成后停止，不无限“进一步完善”。
