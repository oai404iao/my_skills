# 原生 workspace、持续集成与回收

创建或分配代码写入工作区前读取“创建与核实”和“基线与写入隔离”；交付 / 整合前读取“切片交付与集成”；每次回收前读取“归档与分支清理”。实际参数始终以当前工具 schema 为准。

## 创建与核实

有代码写入的独立 Paseo 执行角色使用 Paseo 原生 `create_workspace` 创建 worktree 隔离的 workspace，再在创建 agent 时显式传入返回的 `workspaceId`。只创建 agent 不会证明 worktree 已隔离；不同 workspaceId 也可能引用同一目录。

新建独立分支时，核实当前接口支持的 worktree isolation、branch-off 模式、源 checkout、基线 ref 和新分支字段。当前接口用 `path` 指定源 checkout、`baseBranch` 指定基线、`branchName` 指定新分支；这是核对线索，不是跨版本固定 API。

操作顺序：

1. 核实项目指令、源 checkout、Git 状态、基线 ref 及解析后的 commit。明确本地分支或远程跟踪 ref，不依赖含糊默认值。
2. 检查创建时会执行的 setup 及其他生命周期钩子，确认副作用处于授权范围内。
3. 调用原生 workspace 创建工具。根据返回核对实际路径、分支和 HEAD 是否符合预期；有偏差先查明，不直接开工。
4. 将执行角色显式绑定到返回的 workspaceId，再登记 agent ID、workspaceId、实际路径、分支、基线 commit 和 ownership。

不猜 Paseo 托管目录布局、内部标识或 provider/model。不得用 `git worktree add`、复制仓库或手选托管目录替代原生生命周期；原生能力不可用时报告相关阻塞，不擅自绕过。

## 基线与写入隔离

- 指定专用任务集成分支及集成工作区，保护用户起始工作区。需要新建 worktree 时同样经原生 workspace 创建；任务集成工作区与最终交付分支默认保留。
- 执行切片从明确任务基线创建；后续切片默认基于最新已集成版本，而非始终从主分支或 `origin/main` 重新分叉。
- worktree 不自动包含其他目录的未提交修改。若依赖起始 dirty 状态，先确认哪些属于本任务和交接方式；不擅自 stash、提交、丢弃或复制整个 dirty 仓库。
- 先收敛当前切片必需的跨模块接口，再并行实现；不让多个工作区同时修改同一不稳定接口。变更时由接口 owner 通知直接消费者，不让所有角色持续追逐接口变化。
- 共享 lockfile、生成文件和公共入口指定一个写入 owner；Pi 内部 subagent 也受所属角色写区限制，不自动获得文件系统隔离。
- Git 隔离不等于运行环境隔离。检查共享 `.venv`、数据库、可变缓存和固定端口；按项目既有方式提供必要隔离，不为任务搭建环境管理平台。
- 创建或归档前检查实际 setup / teardown。原生钩子不构成真实迁移、业务写入或数据删除授权；发现越权副作用先停止相应操作并报告。
- 编排者、监督者、唯一任务表及需保留的验证证据不放在会提前清理的执行 workspace 中。

## 切片交付与集成

采用项目已有的简单 Git 集成方式，不额外规定分支名、commit 格式或合并策略。已获本地提交授权时优先小而完整的提交；提交与整合授权分别判断，不把本地提交许可当成主分支合并许可。

### 模块负责人

- 将工作拆成可独立验证的交付切片，运行相关检查；满足条件即通知集成 owner，不等整个模块结束。
- 交付 commit 或明确基线的可应用 diff，包含必要新增文件、行为变化、检查及对应版本、剩余问题和接口偏差。
- 已交付 commit 不再改写，后续修正用新提交。只有相关依赖或接口变化时才同步基线，不因无关合入要求所有 worktree rebase。
- 处理本模块冲突与语义问题，不自行向任务集成分支合并或偷偷回写集成工作区。

### 集成 owner

- 同一时刻独占任务集成分支及其工作区写入。交接前说明当前版本、未完成操作和 ownership，避免双写。
- 按依赖顺序接收切片，在集成工作区执行获准的实际整合；下一轮调度优先处理可合入交付，不边积压边扩大团队。
- 检查跨模块契约与合入后的受影响行为，记录交付源版本、集成结果版本和实际验证，不以各模块独立通过替代集成运行。
- 冲突由相关模块负责人解决语义，集成 owner 协调依赖并负责最终落入集成版本；不要把所有修复收回编排者串行做，也不能覆盖他人已集成成果来强行消除冲突。
- 集成失败时记录失败版本、责任模块与修复动作；必要时仅撤销该次集成，不破坏其他已集成结果，不继续堆叠依赖失败版本的变更。

唯一集成 owner 是写入责任，不是所有设计、diff、测试的逐项审批人。先跑通最小纵向闭环，再逐块扩展，避免积累组合从未运行的补丁。

### 无提交或整合授权

未获本地提交授权时，以明确基线的可应用 diff 及必要新增文件交接，不偷偷提交。由集成 owner 在用户允许的整合方式内落盘；整合涉及生成提交时，需确认相应授权，不把“可应用 diff”视作提交许可。

未获相应整合授权则保留交付并报告阻塞。区分模块已交付、已集成、集成验证通过、最终验收通过；未实际进入集成版本不能报告已合并。

## 归档与分支清理

集成 owner 负责回收本任务执行 workspace；执行角色只报告“可回收”。交付完整集成、相关集成验证通过且不再需要时，在授权范围内及时原生归档，不统一拖到任务结束。

### 每次归档前确认

- 交付已完整进入明确集成版本，并有相应验证；工作区 clean 本身不证明已集成。squash / cherry-pick 不能只靠 commit 祖先关系判断，应核对实际变更与集成记录。
- 没有未整合提交或未提交修改；没有需要保留但尚未保存的未跟踪 / 忽略文件。
- 没有仍使用目录的执行成员、测试或服务；不能靠归档顺便终止未知工作。
- 必要交付说明与验证证据已保存到不会随 workspace 删除的位置。
- teardown 的实际影响处于授权范围内。
- 已取得对应 workspace 与本地任务分支的清理授权，且资源确为本任务新建的执行资源。

### 原生生命周期与结果核实

1. 使用 Paseo 原生 `archive_workspace`。归档不只是隐藏：可能归档所属会话 / 终端、执行 teardown，并在最后一个活动 workspace 引用消失后移除托管 worktree。按当前工具和项目钩子核实实际影响。
2. 核对归档、钩子及 worktree 的实际结果。请求被接受不等于全部清理完成；若仍被其他 workspace 引用或清理失败，记录具体原因，不强行移除。
3. 不假设归档删除本地分支。确认交付已保留、无 worktree 仍使用该分支且获得删除授权后，再清理对应本地任务分支。工具拒绝删除时先查明原因，不用强制删除绕过保护；无法安全完成则保留并报告。
4. 更新唯一当前任务表，记录清理结果或保留原因。

禁止直接 `rm -rf` 托管目录、强制 `git worktree remove` 或手改 Paseo 内部登记绕过生命周期。不清扫其他任务的 workspace、临时目录、分支或远程资源。

未集成、验证失败、仍需排障或含未保留成果的 workspace 不自动归档。任务取消不授权丢弃成果；未获清理授权只列待回收资源。既有 workspace、用户原有分支、起始修改、他人工作、集成工作区及最终交付分支均不在默认清理范围。
